# Технічні вимоги до додатка (add-on) для NVDA: "Глобальний Чекліст Тестувальника"

## 1. Загальний опис проекту
Додаток призначений для незрячих спеціалістів із тестування та розробників. Він дозволяє проходити чеклісти перевірки програмного забезпечення за допомогою глобальних гарячих клавіш NVDA, повністю зберігаючи системний фокус на тестованому застосунку. Вся взаємодія (навігація, зміна статусів, отримання контексту) відбувається через мовленнєвий супровід скрінрідера без відкриття додаткових вікон під час роботи.

**Підтримувані мови інтерфейсу — англійська та українська.** Мова визначається мовою інтерфейсу NVDA; окремого налаштування мови в додатку немає. Механізм локалізації описано в §6.

## 2. Формат даних та архітектура збереження
* **Формат файлів**: Конфігурація та списки завдань зберігаються у файлах формату JSON (наприклад, `checklist.json`).
* **Структура JSON**: Файл повинен мати чітку ієрархічну структуру, яка підтримує розділи та завдання всередині них.
  * *Обов'язкові умови структури*: наявність мінімум одного розділу (`sections`) є обов'язковою; плоскі списки без розділів не підтримуються.
  * *Опис полів*:
    * `format_version` *(ціле число, **необов'язкове**, за замовчуванням `1`)*: версія формату файлу. Поле верхнього рівня. Призначене не для міграції, а для **розпізнавання**: майбутня версія додатка зможе повідомити *"Файл створено новішою версією додатка"* замість того, щоб впасти на невідомому значенні з неінформативним *"Помилка читання файлу"*.
    * `checklist_name` *(рядок, обов'язкове)*: назва чекліста.
    * `sections` *(масив, обов'язкове)*: масив розділів. Мінімум один елемент.
    * `section_name` *(рядок, обов'язкове)*: назва розділу.
    * `items` *(масив, обов'язкове)*: масив пунктів у розділі.
    * `id` *(ціле число, обов'язкове)*: унікальний ідентифікатор пункту в межах файлу.
    * `text` *(рядок, обов'язкове)*: текст пункту, який озвучується.
    * `status` *(рядок, **необов'язкове**, за замовчуванням `"pending"`)*: стан перевірки пункту. Допустимі значення та їхні формулювання наведено в таблиці нижче. Відсутність поля еквівалентна `"pending"`.
    * `note` *(рядок, **необов'язкове**)*: підказка або коментар до пункту. Озвучується автоматично після тексту пункту. Призначений лише для читання; додається вручну або генерується Claude.
    * `comment` *(рядок, **необов'язкове**)*: висновок тестувальника за результатом перевірки.
  * *Словник статусів*: наведені слова є **єдиним** джерелом формулювань для всього додатка — озвучення статусу (§3.3), озвучення зміни (§4) та префікса у дереві GUI (§5). Реалізуються однією таблицею в коді; окремих формулювань під кожен контекст бути не повинно.

    | `status` | Слово озвучення | Префікс у дереві GUI |
    |---|---|---|
    | `"pending"` | не перевірено | *(відсутній)* |
    | `"passed"` | пройдено | `Пройдено: ` |
    | `"failed"` | провалено | `Провалено: ` |
    | `"blocked"` | заблоковано | `Заблоковано: ` |
    | `"skipped"` | пропущено | `Пропущено: ` |

    `pending` навмисно не має префікса в дереві: це найчастіший стан, і слово перед кожним із десятків пунктів коштувало б користувачеві більше, ніж дає. Відсутність префікса й означає «не перевірено».

    **Значення поля `status` є ідентифікаторами, а не текстом, і не локалізуються**: `"passed"` лишається `"passed"` за будь-якої мови інтерфейсу. Локалізуються лише колонки слів. Інакше чекліст, збережений в українському NVDA, було б неможливо прочитати в англійському, і формат перестав би бути переносним. Наведені слова нормативні для локалі `uk`; англійські оригінали (`msgid`) — див. §6.

    **Вміст чекліста є даними користувача, а не інтерфейсом**: `checklist_name`, `section_name`, `text`, `note` і `comment` не перекладаються ніколи й жодним механізмом.
  * *`note` проти `comment`* — поля навмисно розрізнені й **не** взаємозамінні:

    | | `note` | `comment` |
    |---|---|---|
    | Коли з'являється | **до** перевірки | **після** перевірки |
    | Хто пише | автор чекліста (вручну або Claude) | додаток, за командою тестувальника (§3.3) |
    | Озвучення | автоматичне, після тексту пункту | лише на запит; наявність позначається (§3.3) |
    | Доля при скиданні | зберігається | **стирається** (§3.2, §5) |

    `comment` доступний за **будь-якого** статусу, а не лише за `"failed"` — висновок на кшталт «пройшло, але повільно» так само вартий запису.
  * *Контракт валідації*: перевіряється **одним проходом при завантаженні файлу**. Будь-яке порушення означає відмову завантажити файл цілком та озвучення *"Помилка читання файлу"* (§4).
    * Наявність усіх обов'язкових полів та відповідність їхніх типів опису вище.
    * Мінімум один розділ у `sections`; `sections` та `items` — саме масиви.
    * Унікальність `id` у межах файлу.
    * Значення `status` належить множині з п'яти допустимих. **Невідоме значення — фатальне**, тиха нормалізація до `"pending"` заборонена: §2 вимагає перезапису всього файлу при першій же зміні, тож нормалізація означала б безповоротне стирання результатів, які користувач туди записав.
    * **Невідомі поля помилкою не є** — вони ігноруються при читанні (див. правила запису).
    * Сувора перевірка типів обов'язкова саме тому, що альтернатива — виключення посеред сесії, коли фокус у тестованому застосунку і NVDA раптом замовкає. Незрячий користувач не побачить traceback; одна зрозуміла відмова при завантаженні незрівнянно краща за тишу через годину роботи.
    * Голосом озвучується лише коротке *"Помилка читання файлу"* (§4 забороняє діалоги в цьому сценарії). **Деталі валідації показує GUI** при виборі файлу (§5).
  * *Правила запису*:
    * `status` записується **завжди явно**, для кожного пункту, включно з `"pending"`.
    * `format_version` записується завжди явно.
    * `comment`, що є порожнім або складається лише з пробільних символів, **не записується** — ключ вилучається. При читанні `""` і пробільний рядок трактуються як відсутнє поле. Це свідомий виняток із правила «явне при записі»: `status` має осмислене значення за замовчуванням, яке варто зафіксувати, а `comment` порожнього осмисленого значення не має — «коментар відсутній» і «коментар порожній» це один стан, і канонічна його форма одна. Нормалізація виконується в одній точці при записі, а не перевірками `if comment` у кожному місці споживання.
    * **Невідомі поля зберігаються при перезаписі**. Збереження мутує завантажену структуру, а не збирає новий об'єкт зі схеми. Без цього перше ж натискання пробілу стирало б дописані вручну або згенеровані Claude дані — той самий клас втрати, від якого захищає фатальність невідомого `status`.
  * *Приклад структури*:
    ```json
    {
      "format_version": 1,
      "checklist_name": "Тестування доступності форми",
      "sections": [
        {
          "section_name": "Елементи керування",
          "items": [
            {"id": 1, "text": "Перевірити доступність кнопок"},
            {"id": 2, "text": "Перевірити фокус на полях введення", "note": "Перевірити Tab та Shift+Tab"},
            {"id": 3, "text": "Перевірити мітки полів форми", "status": "failed", "comment": "Поле «Телефон» без мітки"}
          ]
        },
        {
          "section_name": "Навігація клавіатурою",
          "items": [
            {"id": 4, "text": "Циклічність Tab-навігації у модальному вікні"}
          ]
        }
      ]
    }
    ```
    Пункти 1, 2 і 4 навмисно подані без `status` — так виглядає рукописний чекліст, і всі вони читаються як `"pending"`.
* **Автозбереження**: Будь-яка зміна статусу завдання, зміна поля `comment` або скидання прогресу призводить до негайного перезапису активного JSON-файлу. *Виняток*: перемикання статусу командою `NVDA+Shift+Пробіл` записується на диск із затримкою на час вікна подвійного натискання — див. §3.2. Відкладений запис не є станом, який можна перечекати: **будь-яка інша команда додатка негайно скидає його на диск** (§3.2.3).
* **Збереження стану сесії**: Поточна позиція користувача (шлях до активного файлу, індекс розділу та індекс пункту) зберігається у файлі `state.json` у папці конфігурації NVDA. Стан відновлюється при наступному запуску NVDA, що дозволяє продовжити роботу з того ж місця. Якщо файл, вказаний у `state.json`, не знайдено на диску — NVDA озвучує попередження *"Файл чекліста не знайдено"* та автоматично відкриває GUI для вибору нового файлу.
  * *Стан фільтра (§3.4) у `state.json` **не зберігається***: це тимчасовий робочий режим, і мовчки активний після перезапуску NVDA фільтр робив би частину пунктів недосяжною без видимої причини. При кожному запуску NVDA фільтр вимкнено.

## 3. Керування та система глобальних гарячих клавіш
Усі гарячі клавіші працюють глобально в операційній системі Windows, не перехоплюючи фокус з активного вікна додатка, що тестується.

### 3.1. Навігація по чеклісту
* **`NVDA+Shift+Стрілка вниз`** (одне натискання): Перехід до наступного **пункту** списку.
* **`NVDA+Shift+Стрілка вгору`** (одне натискання): Перехід до попереднього **пункту** списку.
* **`NVDA+Shift+Стрілка вниз`** (подвійне натискання): Перехід до першого пункту наступного **розділу**. При спробі перейти далі останнього розділу — NVDA озвучує "Кінець списку".
* **`NVDA+Shift+Стрілка вгору`** (подвійне натискання): Перехід до першого пункту попереднього **розділу**. При спробі перейти вище першого розділу — NVDA озвучує "Початок списку".
* **Поведінка на межах (одинарна навігація)**: При спробі перейти далі останнього пункту або вище першого пункту, фокус залишається на місці, а NVDA відтворює системний звуковий сигнал (beep) або озвучує повідомлення "Кінець списку" / "Початок списку".
* **Коректність подвійних натискань**: Одинарне натискання спрацьовує миттєво й уже змістить позицію до моменту, коли надійде друге натискання (див. §6). Тому при `repeatCount == 0` скрипт зберігає **початкову позицію серії** (індекс розділу та індекс пункту), а перехід до сусіднього розділу при `repeatCount == 1` обчислюється від цієї збереженої позиції, а не від поточної. Без цього подвійне натискання на останньому пункті розділу пропускало б один розділ.
* **Модель позиції**: Позиція завжди зберігається як реальна пара «індекс розділу + індекс пункту» у **повній** структурі чекліста й не залежить від стану фільтра. Фільтр не будує окремий список і не перенумеровує пункти — він лише звужує сканування (див. §3.4).

### 3.2. Керування статусом перевірки
NVDA виконує скрипт на **кожному** натисканні серії й не чекає її завершення (див. §6), тому перше натискання вже змінить дані до того, як стане відомо про друге. Логіка команд враховує це явно.

Статус виставляється **двома шляхами**: швидким (`NVDA+Shift+Пробіл`) і повним (`NVDA+Shift+S` + цифра, будь-який із п'яти станів). Жоден із них **ніколи не змінює системний фокус** — це недоторкана інваріанта продукту (§1), а не зручність.

#### 3.2.1. Швидкий шлях (`NVDA+Shift+Пробіл`)
* **Одне натискання**: Перемикання між `"passed"` та `"pending"` — приблизно 90% натискань за сесію.
  * *Правило переходу є тотальним*: якщо поточний статус `"passed"` → стає `"pending"`; за **будь-якого іншого** статусу (`"pending"`, `"failed"`, `"blocked"`, `"skipped"`) → стає `"passed"`. Перемикач із третього стану інакше невизначений.
  * Зміна застосовується в памʼяті та озвучується миттєво, а **запис на диск відкладається** на `multiPressTimeout + 50 мс` (значення береться з конфігурації NVDA, див. §6) — це вікно, у якому ще може надійти друге натискання.
* **Подвійне натискання**: Повне скидання **поточного розділу** — для всіх його пунктів встановлюється `status: "pending"` **і стирається поле `comment`**.
  * *Чому стирається `comment`*: коментар, що пережив скидання, висить на `pending`-пункті й стверджує «провалено, бо X» про пункт, якого ніхто не перевіряв. Це не мертві дані, а дані, які **озвучуватимуться** й дезінформуватимуть; осиротілий коментар неможливо показати чесно.
  * Спершу скрипт **скасовує відкладений запис і відкочує перемикання**, виконане першим натисканням: статус поточного пункту повертається до попереднього значення, файл на диску залишається незмінним.
  * Далі NVDA озвучує запит: *"Скинути розділ? Натисніть ще раз для підтвердження."*
  * **Очікування підтвердження реалізується власним таймером додатка (`wx.CallLater`, 3 секунди), а не механізмом `getLastScriptRepeatCount()`.** Причина: 3 секунди перевищують `multiPressTimeout` (типово 500 мс), тож на момент підтверджувального натискання NVDA поверне `repeatCount == 0`, і без власного стану скрипт просто знову перемкнув би статус поточного пункту.
  * Поки активний стан очікування підтвердження, `NVDA+Shift+Пробіл` не перемикає статус пункту, а виконує скидання розділу.
  * Очікування скасовується таймаутом (3 с), будь-якою іншою гарячою клавішею додатка або зміною позиції.
  * Після виконання скидання скрипт викликає `scriptHandler.clearLastScript()`, щоб наступне натискання почало нову серію.

#### 3.2.2. Повний шлях: префікс-режим (`NVDA+Shift+S`)
П'ять станів проти однієї клавіші не вміщуються ані в цикл, ані в окремі глобальні комбінації. Цикл `pending → passed → failed → blocked → skipped` мертвий за побудовою: §6 трактує швидкі повторні натискання як **серію**, тож чотири натискання заради `"skipped"` дали б `repeatCount == 3` і зіткнулися зі скиданням розділу (§3.2.1); до того ж незрячий користувач мусив би прослухати кожен проміжний стан, а промах вимагав би повного кола. Окремі клавіші на кожен статус також відпадають: `NVDA+Shift+F` уже зайнята фільтром (§3.4), а мнемоніка українських слів колізійна — «**п**ройдено» і «**п**ропущено» ділять літеру.

* **`NVDA+Shift+S`** озброює режим і озвучує підказку: *"Статус: 1 пройдено, 2 провалено, 3 заблоковано, 4 пропущено, 5 не перевірено"*.
* Наступне натискання **цифри** встановлює відповідний статус поточного пункту, озвучує результат і знімає режим:

  | Клавіша | `status` |
  |---|---|
  | `1` | `"passed"` |
  | `2` | `"failed"` |
  | `3` | `"blocked"` |
  | `4` | `"skipped"` |
  | `5` | `"pending"` |

* **Цифри, а не літери** — саме через колізію «пройдено/пропущено»; цифри до того ж мовно нейтральні й повністю перелічені в підказці. Позиція `5` навмисно віддана поверненню в `"pending"`: це слот «відмінити», і §4 спеціально не робить після нього автопереходу.
* Режим живе **3 секунди**, відлічувані власним таймером `wx.CallLater` — з тієї ж причини, що й очікування підтвердження в §3.2.1: `getLastScriptRepeatCount()` тут непридатний.
* Клавіші режиму реєструються через `bindGesture` при озброєнні та знімаються через `clearGestureBindings` при виході.
* **Незв'язана клавіша режим не скасовує**: вона просто надходить у тестований застосунок, а режим доживає до таймауту або до наступної команди додатка. Це свідоме обмеження — перехоплювати довільні клавіші при фокусі в чужому вікні додаток не має права.
* Запис на диск виконується негайно; відкладення (§3.2.1) стосується лише `NVDA+Shift+Пробіл`.

#### 3.2.3. Модальні стани та відкладений запис
У додатку існує три часові стани — відкладений запис (§3.2.1), очікування підтвердження скидання (§3.2.1) та префікс-режим статусу (§3.2.2). Вони узгоджуються двома правилами, які знімають увесь клас гонок структурно, а не перевірками:

1. **Відкладений запис — не модальний стан, а борг.** Будь-яка інша команда додатка **негайно скидає його на диск** (flush), не чекаючи таймера. Тому питання «що потрапить у файл, якщо `NVDA+Shift+S 1` натиснуто всередині вікна відкладеного запису» не виникає взагалі.
2. **Модальний стан щонайбільше один.** Озброєння будь-якого з них знімає інший. Будь-яка команда додатка, крім власних клавіш активного режиму, знімає режим і **виконується як звичайно**.

* Повідомлення *"Скасовано"* озвучується **лише при скасуванні за таймаутом**. При скасуванні іншою командою озвучується результат самої команди — інакше стрілка вниз читала б *"Скасовано. Перевірити фокус на полях введення"*, де перше слово є чистим шумом про дію, якої користувач не робив.

### 3.3. Запит інформації (`NVDA+Shift+I`)
Дії в серії побудовані за принципом **наростання**, як у вбудованих командах NVDA (`NVDA+T`, `NVDA+C`, `NVDA+End`): перші натискання виконують лише озвучення, і тільки останнє натискання виконує «важку» дію зі зміною фокуса. Це обовʼязкова умова, а не стильова вподоба — NVDA виконує скрипт на кожному натисканні серії (див. §6), тож діалог, відкритий на другому натисканні, перехопив би фокус і зробив третє натискання недосяжним.

* **Одне натискання**: Повторити озвучення тексту та статусу поточного пункту. Якщо пункт має поле `note` — воно озвучується автоматично після тексту. Якщо пункт має непорожній `comment` — після статусу додається маркер *", є коментар"*; **сам текст коментаря автоматично не озвучується**.
  * *Чому маркер, а не текст*: `note` пише автор чекліста, він короткий і призначений, щоб його чули щоразу. `comment` пише тестувальник у текстовому полі, і це може бути абзац — озвучувати його при кожному проході повз пункт означало б карати користувача за докладність. Два слова замість абзацу: нуль шуму за замовчуванням, короткий сигнал за наявності, деталі на запит (потрійне натискання).
  * Порядок озвучення — текст → статус → нотатка. Він навмисно **зворотний** до порядку в дереві GUI, де статус іде префіксом перед текстом (§5): дерево скануєш вертикально, і префікс дає фільтр на слух із першого складу, тоді як тут пункт лише один, і його текст важливіший за вердикт.
* **Подвійне натискання**: Озвучити назву поточного розділу та прогрес у ньому: *"Розділ: Елементи керування, опрацьовано 4 з 5"*. Якщо в розділі є провалені пункти — додається *", провалено N"*: *"Розділ: Елементи керування, опрацьовано 4 з 5, провалено 1"*.
  * **Опрацьованим** вважається пункт із будь-яким статусом, окрім `"pending"`. Слово «виконано» вжити не можна: при п'яти станах воно не означає нічого конкретного.
  * Згадка провалених з'являється **лише за їх наявності**. Нуль шуму, коли все гаразд; гучно, коли ні.
* **Потрійне натискання**: Відкрити **діалог пункту** — `wx.Dialog` з трьома полями `wx.TextCtrl`:
  * **"Пункт"** *(read-only)* — повний текст поля `text` поточного пункту.
  * **"Нотатка"** *(read-only)* — вміст поля `note` (якщо відсутнє — поле відображається з міткою *"Нотатка відсутня"*).
  * **"Коментар"** *(редаговане)* — вміст поля `comment`. Це єдине місце в додатку, де вводиться текст коментаря.
  * Кнопки *"Зберегти"* та *"Скасувати"*. Escape дорівнює *"Скасувати"*. Збереження записує файл негайно і є «іншою командою» в сенсі §3.2.3, тобто скидає відкладений запис. Порожній або пробільний коментар при збереженні вилучається з файлу (§2, правила запису).
  * Навігація між полями клавішею Tab. Кожне поле дозволяє посимвольну навігацію стрілками, виділення (Shift+стрілки) та копіювання (Ctrl+C).
  * Після відкриття діалога скрипт викликає `scriptHandler.clearLastScript()`, щоб четверте натискання не намагалося відкрити друге вікно поверх уже відкритого.
  * Це єдина команда додатка, яка змінює системний фокус. Оскільки вона стоїть останньою в серії, випадкове відкриття вікна під час роботи з тестованим застосунком виключене. **Ввід коментаря навмисно поселено сюди, а не на власну гарячу клавішу, саме щоб це твердження залишалося істинним**: друга команда з фокусом зруйнувала б центральну гарантію безпеки продукту заради поля, яке заповнюють рідко.

### 3.4. Фільтрація списку (`NVDA+Shift+F`)
* **Одне натискання**: Увімкнення або вимкнення режиму **"Тільки неперевірені пункти"**. NVDA озвучує поточний стан: *"Фільтр увімкнено"* або *"Фільтр вимкнено"*. Якщо фільтр вмикається, коли неперевірених пунктів не залишилося взагалі — NVDA озвучує *"Фільтр увімкнено. Неперевірених пунктів немає"*.

**Модель реалізації.** Фільтр реалізується як **предикат видимості** `visible(item)`, що застосовується під час сканування структури, а **не** як побудова окремого масиву видимих пунктів із власною нумерацією. При увімкненому фільтрі предикат є буквально `item.status == "pending"`; при вимкненому — тотожно істинний. Наслідки, які є обовʼязковими вимогами:

* **Фільтр показує лише `"pending"`**, а не «все, що не пройдено». Фільтр існує, щоб дійти до того, чого користувач **ще не дивився**; у решти чотирьох станів вердикт уже записано. Повторний прогін після виправлення — окремий сценарій, і він обслуговується скиданням розділу (§3.2.1). Саме тому режим зветься «Тільки неперевірені», а не «Тільки невиконані»: друга назва при п'яти станах була б неправдивою.
* **Єдиний шлях коду для навігації**: і одинарне, і подвійне натискання (§3.1) — це та сама операція «сканувати вперед/назад до першого елемента, що задовольняє предикат», з різною точкою старту (поточна позиція / якір серії) та різним кроком (пункт / розділ). Окремих гілок `if фільтр увімкнено` в навігації бути не повинно.
* **Поточний пункт може не задовольняти предикат** — і це коректний стан, а не помилка. Наприклад, коли пункту присвоєно `"passed"` при вимкненому автопереході (§4): позиція залишається на ньому, а наступне натискання стрілки природно перейде до наступного видимого пункту. Модель «масив видимих пунктів» цей стан виразити не може й породжує помилки індексації.
* **Розділи без жодного неперевіреного пункту пропускаються**: при увімкненому фільтрі подвійне натискання `NVDA+Shift+Стрілки` шукає найближчий розділ, у якому є **хоча б один** пункт, що задовольняє предикат. Якщо таких розділів попереду (або позаду) немає — NVDA озвучує *"Кінець списку"* / *"Початок списку"*.
* **Перемикання фільтра не змінює позицію**: `NVDA+Shift+F` — це зміна режиму, а не команда навігації. Скрипт озвучує лише стан фільтра й ніколи не переміщує користувача, навіть якщо поточний пункт після вмикання фільтра стає невидимим.
* **Прогрес рахується завжди по повному розділу**, незалежно від стану фільтра: *"Розділ: Елементи керування, опрацьовано 4 з 5"* (див. §3.3). Рахувати прогрес лише за видимими пунктами заборонено — це давало б неінформативне *"опрацьовано 0 з 1"*.

### 3.5. Переназначення клавіш
Усі скрипти додатка доступні для переназначення через вбудований діалог NVDA **"Жести вводу"** (NVDA-меню → Параметри → Жести вводу). Для цього кожен скрипт повинен мати заповнений параметр `description` у декораторі `@script`, загорнутий у `_()` (§6). Окремий UI для переназначення клавіш у додатку не реалізується.

* *Виняток*: цифри префікс-режиму (§3.2.2) зв'язуються динамічно через `bindGesture` лише на час дії режиму й **не з'являються** в діалозі «Жести вводу». Переназначенню підлягає сама комбінація `NVDA+Shift+S`, а не цифри всередині режиму.

## 4. Взаємодія зі скрінрідером та логіка поведінки

* **Виведення мовлення**: Усі інформаційні повідомлення надсилаються до синтезатора мовлення через стандартну функцію API NVDA `ui.message()`. Текст кожного повідомлення загортається у `_()` (§6).
* **Формулювання статусів**: Єдиним джерелом слів є словник статусів у §2. Дублювати формулювання по місцях використання заборонено.
* **Логіка автопереходу**: У налаштуваннях додатка має бути доступна опція автопереходу.
  * *Якщо увімкнено*: Після присвоєння пункту будь-якого **вердикту** — тобто будь-якого статусу, окрім `"pending"` — внутрішній фокус додатка автоматично переміщується на наступний **видимий** пункт (за предикатом §3.4: при увімкненому фільтрі це наступний `"pending"`, при вимкненому — буквально наступний), і він одразу озвучується.
  * *Повернення в `"pending"`* (цифра `5`, §3.2.2, або перемикання пробілом із `"passed"`) автопереходу **не викликає**. Правило: *перехід після вердикту, зупинка після виправлення* — повернення в `"pending"` означає, що користувач виправляє помилку й хоче лишитися на пункті, щоб перечитати його. Інакше слот «відмінити» був би непридатним.
  * *Якщо видимого наступного пункту немає*: позиція залишається, **без** сигналу межі та без повідомлення. Користувач не давав команди навігації, і beep тут повідомляв би про неіснуючу помилку.
  * *Якщо вимкнено*: Фокус залишається на поточному пункті, NVDA просто озвучує зміну статусу.
* **Сповіщення про завершення чекліста**: Якщо після присвоєння статусу в усьому чеклісті не залишилося жодного пункту зі статусом `"pending"`, NVDA додатково відтворює звуковий сигнал і озвучує повідомлення *"Чекліст завершено! Опрацьовано всі N пунктів"*; за наявності провалених додається *", провалено M"*. Повідомлення виводиться незалежно від налаштування автопереходу.
  * Умова навмисно збігається з предикатом фільтра (§3.4) та з підрахунком прогресу (§3.3) — три різні поведінки, один вимір, нуль розбіжностей у коді. Вимога «всі `"passed"`» означала б, що чекліст із одним проваленим пунктом ніколи не «завершується», хоча робота скінчена.
* **Обробка граничних станів**: При спробі використати гарячі клавіші без завантаженого файлу — NVDA озвучує *"Чекліст не завантажено"*. При будь-якому провалі завантаження — *"Помилка читання файлу"* без додаткових діалогів. Під це повідомлення підпадають: помилка парсингу JSON, невідоме значення поля `status` та будь-яке порушення контракту валідації типів (§2). Деталі причини показує GUI (§5).

## 5. Графічний інтерфейс користувача (GUI)
Для адміністрування додаток повинен мати візуальне вікно налаштувань, інтегроване в структуру NVDA.

* **Технологія**: Реалізація на базі бібліотеки `wxPython` (вбудованої в середовище розробки аддонів NVDA).
* **Доступність**: Повна доступність усіх елементів керування для екранного читця (коректні класи вікон, наявність текстових міток, підтримка стандартної клавіатурної навігації Tab/Shift+Tab).
* **Точка входу**: Меню NVDA -> Інструменти -> Глобальний Чекліст Тестувальника.
* **GUI призначений лише для перегляду та адміністрування.** Редагування статусів і коментарів через дерево **не реалізується**: це був би другий шлях запису в той самий файл, який паралельно перезаписується глобальними командами, а розсинхрон між відкритим вікном і зміненим файлом — дефект, за який не варто платити в MVP. Ввід коментаря живе виключно в діалозі §3.3.
* **Компоненти та функціонал вікна GUI**:
  * Кнопка огляду (`Browse...`) та текстове поле для вибору активного файлу `checklist.json` з диска. Якщо вибраний файл не проходить контракт валідації (§2) — GUI показує **конкретну причину** (яке поле, який пункт, яке значення), на відміну від короткого голосового *"Помилка читання файлу"*.
  * Деревоподібний список (`wx.TreeCtrl`) або список для візуального перегляду повної структури розділів та завдань вибраного чекліста. Статус кожного пункту відображається **текстовим префіксом у мітці вузла** згідно зі словником §2; пункти зі статусом `"pending"` префікса не мають.
  * **Read-only панель під деревом**, що показує поле `comment` вибраного пункту. Коментар навмисно не потрапляє в мітку вузла: §2 тримає мітки короткими, і абзац у мітці скасував би цю властивість.
  * Прапорець (Checkbox) для увімкнення/вимкнення опції "Автоматично переходити до наступного пункту після відмітки".
  * Кнопка "Скинути весь прогрес", яка встановлює `status: "pending"` для всіх завдань у поточному файлі **та стирає всі поля `comment`**. Перед виконанням відображається стандартний діалог підтвердження NVDA (`MessageDialog`) з повідомленням *"Скинути весь прогрес? Будуть стерті всі статуси та коментарі. Цю дію не можна відмінити."* та кнопками "Так" і "Ні".

## 6. Технічні параметри розробки
* **Тип додатка**: Глобальний плагін NVDA (`globalPluginHandler.GlobalPlugin`).
* **Мова розробки**: Python 3 (відповідно до версії Python, що використовується в поточній архітектурі NVDA).
* **Обробка серій натискань**: Реалізація виключно через `scriptHandler.getLastScriptRepeatCount()`. Функція повертає `0` для першого натискання в серії, `1` для другого, `2` для третього і далі — **верхньої межі немає**, тож потрійні натискання підтримуються нарівні з подвійними (вбудовані команди NVDA `NVDA+T`, `NVDA+C`, `NVDA+End` використовують саме три рівні). Власне вимірювання часу між викликами скриптів не потрібне й не допускається.
  * Функції `scriptHandler.getLastScriptExecutionTime()` в API NVDA **не існує**. Доступні `scriptHandler.getLastScriptRepeatCount()` та `scriptHandler.clearLastScript()`.
  * Інтервал відраховується між двома **сусідніми** натисканнями серії (а не на всю серію) і визначається налаштуванням NVDA `config.conf["keyboard"]["multiPressTimeout"]`: типово 500 мс, діапазон 100–20000 мс, змінюється користувачем у *Параметри NVDA → Клавіатура → «Тайм-аут кількох натискань клавіш (мс)»*. Додаток **не має права хардкодити 500 мс** — усі власні затримки (зокрема відкладений запис у §3.2) обчислюються від актуального значення `config.conf`.
  * NVDA виконує скрипт на кожному натисканні серії й **не чекає** її завершення. Тому дії проєктуються за принципом наростання: озвучення → озвучення → «важка» дія (діалог, зміна даних, буфер обміну) лише на останньому натисканні. Альтернатива з відкладеним запуском кожної дії через `core.callLater` відхилена: вона додала б ~0.5 с затримки до **кожного** одинарного натискання, що неприйнятно для основних команд навігації та озвучення.
  * Лічильник серії глобальний і привʼязаний до конкретної функції-скрипта: виконання будь-якого іншого скрипта NVDA між натисканнями скидає його в `0`. Логіка додатка не повинна покладатися на те, що серія обовʼязково дійде до кінця.
* **Стани, що не є серіями**: очікування підтвердження скидання (§3.2.1) та префікс-режим статусу (§3.2.2) **не використовують** `getLastScriptRepeatCount()`. Обидва відлічують 3 секунди власним `wx.CallLater`, бо цей інтервал перевищує `multiPressTimeout` і NVDA на момент другого натискання повернув би `repeatCount == 0`. Клавіші префікс-режиму реєструються через `bindGesture` і знімаються через `clearGestureBindings`.
* **Дисципліна запису на диск**: відкладений запис (§3.2.1) скидається на диск будь-якою іншою командою додатка, не чекаючи таймера (§3.2.3). Реалізація не повинна покладатися на спрацювання таймера як єдиний шлях збереження.
* **Локалізація**: Додаток підтримує дві мови інтерфейсу — **англійську та українську** — через стандартний для NVDA механізм `gettext`.
  * **Мовою оригіналу (`msgid`) є англійська.** Усі рядки інтерфейсу записуються в коді англійською й загортаються у `_()`. Українська постачається як каталог перекладу; формулювання, наведені в цій специфікації, нормативні саме для локалі `uk`.
  * Каталоги перекладу: `addon/locale/<lang>/LC_MESSAGES/nvda.po`, що компілюються в `.mo`. Перекладні поля `manifest.ini` (`summary`, `description`) — у `addon/locale/<lang>/manifest.ini`.
  * Кожен модуль, що використовує `_()`, викликає `addonHandler.initTranslation()`.
  * Параметр `description` у декораторі `@script` (§3.5) також загортається у `_()`, інакше діалог «Жести вводу» показував би англійські описи в українському NVDA.
  * Мова визначається мовою інтерфейсу NVDA. **Окремого налаштування мови в додатку немає** — користувач обрав мову один раз, у параметрах скрінрідера, і другий перемикач лише розійшовся б із першим.
  * Локалізація не поширюється на значення поля `status` та на вміст чекліста — див. §2.
* **Сумісність**: Додаток має відповідати актуальним вимогам до розробки аддонів NVDA, підтримувати актуальні версії API та коректно опрацьовувати структуру метаданих у файлі `manifest.ini`.

## 7. Дорожня карта (поза MVP)
Функціонал, узгоджений до реалізації в майбутніх версіях після стабільного MVP:

* **Швидке перемикання між чеклістами** (`NVDA+Shift+N`): голосове меню зі списком останніх 5 відкритих файлів без відкриття GUI.
* **Експорт/звіт**: команда для генерації текстового або Markdown-звіту з групуванням пунктів за статусами та з їхніми коментарями.
* **Редактор нотаток**: команда для додавання/редагування поля `note` (підказки автора чекліста) прямо під час тестування. Редагування поля `comment` до дорожньої карти не належить — воно реалізоване в MVP (§3.3).
* **Історія прогонів**: збереження послідовності вердиктів по кожному пункту замість одного поточного статусу. Потребує перегляду правила §3.2.1 про стирання `comment` при скиданні — історія, яку стирає скидання, історією не є.
