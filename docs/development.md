# Розробка: середовище та цикл перевірки

Цей файл описує **процес** — як зібрати додаток і як бачити правки в живому NVDA.

Про **поведінку** додатка — [`requirements.md`](requirements.md). Усе, що стосується самого артефакта (структура `addon/`, генерований `manifest.ini`, джерело версії, локалізація), нормативно описано в §6 спеки; тут воно лише використовується.

## 1. Передумови

* **Python 3.13** — версія з `.python-version`; та сама, що її виконує NVDA стелі: `pyproject.toml` NVDA 2026.2 вимагає `>=3.13,<3.14`, тож тести ядра йдуть на тому Python, що й скрінрідер (§6 спеки).
* **SCons ≥ 4.10.1** — збірка.
* **GNU gettext** (`msgfmt`, `xgettext`) — компіляція `.po` у `.mo`. Windows-збірки: [gettext-iconv-windows](https://mlocati.github.io/articles/gettext-iconv-windows.html).
* **Markdown ≥ 3.8.2** — генерація HTML з документації.
* **`uv`** — dev-залежності шаблону (Ruff, Pyright, `prek`) із закріпленими версіями. `uv run prek install` вмикає ті самі перевірки, що й CI, на кожному коміті; `uv run prek run --all-files` проганяє їх по всьому репозиторію. Можна нічого не ставити глобально: `uv run --group build scons` бере закріплений SCons.
* Один раз варто налаштувати фільтр, що прибирає номери рядків із `.po` (на нього вказує `.gitattributes`):

```
git config --global filter.cleanpo.clean "msgcat - --no-location"
```

* П'ять відхилень від шаблону, зроблених свідомо:
  * хук `no-commit-to-branch` вилучено з `prek.toml`: він стереже `main` і `master`, а `git flow release finish` робить на `main` merge-коміт щоразу, коли злиття не fast-forward — тобто коли `main` зрушила з моменту відгалуження, як воно й буває після хотфікса (§7). Зупинений посеред операції, `finish` лишає реліз злитим наполовину, і це дорожче за користь від хука; політика гілкування живе в `CLAUDE.md`;
  * оболонку аддона — модулі, що імпортують NVDA, — виключено з локальної перевірки Pyright у `pyproject.toml`: модулі NVDA (`globalPluginHandler`, `addonHandler`, …) розв'язуються лише проти вихідників NVDA, і без них сувора перевірка сипле помилками на кожному символі. Ядро `core/` лишається під локальною перевіркою, а оболонку перевіряє CI проти вихідників NVDA — див. нижче;
  * адресу для звітів перекладачів у `sconstruct` змінено зі списку спільноти NVDA на issue-трекер проєкту: у той список наші рядки не потрапляють;
  * `pythonSources` у `buildVars.py` зроблено рекурсивним (`**/*.py`): у додатка є підпакети — див. «Межа ядра й оболонки» нижче, — і без цього правка в підпакеті не змусила б `scons` перезібрати `.nvda-addon`, ані дійшла б до `scons pot` через `i18nSources`;
  * `checks.yml` іде на `windows-latest`, а не на Ubuntu, як решта workflow шаблону: перевірка типів потребує wxPython, коліс якого для Linux на PyPI немає — sdist збирає wxWidgets із вихідників, — а сам аддон працює лише на Windows, тож і юніт-тести ходять по тій файловій системі, яку зустрінуть у скрінрідері.

## 2. Перша збірка

```
scons
```

Створює:

* `addon/manifest.ini` — з `manifest.ini.tpl` і `buildVars.py`;
* `addon/locale/<lang>/manifest.ini` — з `.po` і `manifest-translated.ini.tpl`;
* `addon/locale/<lang>/LC_MESSAGES/nvda.mo` — компільовані переклади;
* `<addon_name>-<addon_version>.nvda-addon` у корені репозиторію.

Жоден із цих файлів не комітиться — єдине джерело метаданих `buildVars.py` (§6 спеки).

Де що лежить:

* `readme.md` у корені — це документація **аддона**, а не репозиторію: збірка копіює її в `addon/doc/en/readme.md` і робить із неї `readme.html`, який NVDA відкриває кнопкою довідки. Тому вона англійською (мова оригіналу, §6 спеки), а українська версія — `addon/doc/uk/readme.md`.
* `addon/locale/uk/LC_MESSAGES/nvda.po` — каталог перекладу інтерфейсу. Після зміни рядків у коді: `scons pot` оновлює `axygenChecklist.pot`, далі `msgmerge --update addon/locale/uk/LC_MESSAGES/nvda.po axygenChecklist.pot` доливає нові рядки в каталог.
  * Забути цей крок нічого не ламає — і саме тому його сторожить `tests/unit/test_catalogue.py` (нижче): неперекладений рядок мовчки звучить англійською в українському NVDA.
* `changelog.md` у корені — тіло майбутнього GitHub-релізу: workflow віддає його **цілком** (`body_path`) і дописує знизу SHA256. Тому файл містить **лише ту версію, що виходить**. Історія вже живе у теґах і на сторінці релізів; накопичена ще й тут, вона потрапляла б у тіло кожного наступного релізу — реліз 1.0.0 переказував би читачеві всю дорогу від 0.0.0. Переписують файл у гілці `release/*`, разом із номером версії (§7).
  * Змінників насправді два. Другий — `addon_changelog` у `buildVars.py`: його показує Add-on Store, і це **перекладний** рядок, тож кожна його правка тягне за собою `.po`. Тримай там один рядок на реліз.

Перед першою збіркою в `buildVars.py` мають бути заповнені `addon_minimumNVDAVersion` і `addon_lastTestedNVDAVersion`: з типовим `None` маніфест не пройде перевірку й NVDA просто не завантажить теку. `addon_lastTestedNVDAVersion` тримай не нижчою за `addonAPIVersion.BACK_COMPAT_TO` своєї NVDA — саме це число, а не власну версію, вона порівнює з полем (`addonHandler.addonVersionCheck.isAddonTested`), і аддон, що не пройшов, позначає несумісним і блокує; у лозі це «Add-on axygenChecklist is considered incompatible». У 2026.1–2026.3 це `2026.1.0`; для 2027.1 уже оголошено `2027.1.0`.

## 3. Підключення робочої копії до NVDA

NVDA переглядає `%APPDATA%\nvda\addons\*` і бере кожну теку, у якій читається `manifest.ini` (`addonHandler._getAvailableAddonsFromPath` — звичайні `os.listdir` та `os.path.isdir`). Junction проходить цю перевірку як звичайна тека, тож посилання на `addon/` робить робочу копію встановленим аддоном:

```
powershell -ExecutionPolicy Bypass -File tools\dev-link.ps1
```

Скрипт бере ім'я з `addon_name` у `buildVars.py`, переконується, що `addon/manifest.ini` існує, і створює junction `%APPDATA%\nvda\addons\<addon_name>` → `<репозиторій>\addon`. Junction (`mklink /J`) обрано замість симлінка (`mklink /D`), бо не потребує ані прав адміністратора, ані ввімкненого Режиму розробника Windows.

Після створення посилання **перезапусти NVDA** (`Ctrl+Alt+N`): список аддонів NVDA будує на старті.

Так перевіряється саме той код, що поїде в реліз: працюють `manifest.ini`, перевірка сумісності та `addonHandler.initTranslation()`. Чому не Developer Scratchpad — §8.

### Портативна копія для ризикованих перевірок

*Інструменти → Створити портативну копію* дає NVDA з власною текою конфігурації, тож посилання можна покласти в неї й не чіпати щоденний профіль:

```
powershell -ExecutionPolicy Bypass -File tools\dev-link.ps1 -NvdaConfig D:\nvda-portable\userConfig
```

Дві копії NVDA одночасно не працюють — запуск портативної замінює встановлену, — але експеримент лишається ізольованим від робочого профілю.

## 4. Цикл розробки

* **Код у `addon/globalPlugins/`** — `NVDA+Ctrl+F3` (*Інструменти → Перезавантажити плагіни*). `globalPluginHandler.reloadGlobalPlugins()` викидає з `sys.modules` усе з префіксом `globalPlugins` і імпортує заново; перезапуск NVDA не потрібен.
* **Переклади (`.po`)** — `scons` (перекомпілювати `.mo`), далі перезапуск NVDA.
* **`buildVars.py`, маніфест** — `scons`, далі перезапуск NVDA.
* **Нове посилання, нова тека аддона** — перезапуск NVDA: `addonHandler` будує список аддонів один раз, на старті.

Наслідок для структури коду: **увесь код додатка лежить під `addon/globalPlugins/<пакет>/`**. Модуль поза цим деревом (скажімо, спільна бібліотека в корені `addon/`) не має префікса `globalPlugins`, тому перезавантаження плагінів не викине його з `sys.modules` — у пам'яті лишиться стара версія, і поведінка стане непоясненною.

### Межа ядра й оболонки

Другий наслідок того самого середовища, з іншого боку. NVDA виконує власний Python (3.13 x64 у 2026.x), і тести через `uv` йдуть на такому самому 3.13, — але модулів `ui`, `wx`, `config` і `addonHandler` поза запущеним скрінрідером не існує взагалі. Модуль, що їх імпортує, під `unittest` не лягає — не «важко протестувати», а не імпортується.

Звідси поділ, і він структурний, а не за домовленістю:

| `core/` — тестується | решта пакета — перевіряється на слух |
|---|---|
| модель чекліста, читання, контракт валідації, правила запису (§2) | `GlobalPlugin`, `@script`, жести, режим команд (§3) |
| ідентифікатори статусів і те, які з них є вердиктами (§2, §4) | таблиця слів статусів, загорнутих у `_()` (§2, §6) |
| позиція, `visible()`, сканування, прогрес, умова завершення (§3.1, §3.3, §3.4, §4) | `ui.message` і тони (§4) |
| читання й запис `state.json` (§2) | вікна `wx` (§3.3.1, §5), `config.conf` (§4) |

`core` лежить **усередині** пакета аддона — `addon/globalPlugins/axygenChecklist/core/`, — тож і вимога §6 спеки, і механіка `NVDA+Ctrl+F3` лишаються цілими. Усередині аддона це `from .core import checklist`; у тестах до `sys.path` додається тека самого пакета, і `core` імпортується як звичайний пакет верхнього рівня — батьківський `__init__.py` з його `import addonHandler` при цьому не виконується.

**Сам імпорт і є правилом.** Якщо в `core` потрапить `import ui`, тест не просто впаде — модуль не завантажиться й скаже це прямим текстом. Окремої перевірки писати не треба: зелений тест і є доказом, що ядро вільне від NVDA. Виняток один — `wx`: wxPython у середовищі розробки є, бо його стаби потрібні CI-перевірці типів (див. «Перевірки перед комітом»), тож `import wx` у ядрі імпортувався б мовчки. Його сторожить `tests/unit/test_boundary.py`: імпортує кожен модуль ядра й перевіряє, що `wx` не прийшов слідом.

Виняток другий — `_()`, і він тихіший за перший. NVDA ставить `gettext` у builtins на старті, тож виклик у ядрі не впав би взагалі — він пішов би в каталог **самої NVDA**, де наших рядків немає. Чому це неприпустимо саме в ядрі — §2 спеки, про ідентифікатори `status`. Той самий тест читає кожен модуль ядра як текст і перевіряє, що пошуку в каталозі там немає.

**Заглушок у `sys.modules` тут не буває.** Підміна `ui` чи `wx` на `Mock` зробила б тести зеленими й забрала б рівно ту властивість, заради якої межа існує: код, що тягне NVDA, тихо оселився б у «тестованій» половині, і за півроку ядра не стало б. Та сама конструкція, що й у `test_schema.py` нижче — узгодженість тримає CI, а не чиясь пам'ять.

**Межу знає й локальний Pyright.** `pyproject.toml` виключає з нього саме модулі оболонки, а не `addon/` цілком, тож `core/` проходить strict-перевірку на кожному коміті хуком `prek` — із правилами, яких у CI-конфігурації немає (див. «Перевірки перед комітом»). Новий підпакет оболонки, скажімо тека вікон, дописується в те виключення. Забути це не вийде тихо: перший же `import wx` засипле локальну перевірку невідомими типами.

**Ядро не питає, де що лежить — йому кажуть.** Теку конфігурації NVDA знає `NVDAState.WritePaths.configDir` (вона йде за тією NVDA, що справді запущена, тож портативна копія тримає свій стан біля своєї конфігурації), шлях до чекліста знає файловий діалог; у `core` приходить готовий шлях, а не спосіб його дізнатися. Інакше перший же `import globalVars` зніме все сказане вище.

Словник статусів межу перетинає, а §2 вимагає тримати його одним. Розріз проходить між ідентифікатором і словом: `"passed"` є ідентифікатором, однаковим у файлі й у коді за будь-якої мови (§2), і живе в `core`; «пройдено» є рядком інтерфейсу, загорнутим у `_()`, і живе в оболонці однією таблицею. Інваріанта від цього ціла — таблиця формулювань лишається одна.

### Перевірки перед комітом

Те саме, що проганяє CI:

```
uv run --group lint ruff format --check .
uv run --group lint ruff check .
uv run --group lint pyright
uv run python -m unittest discover -s tests
```

Або одним заходом — `uv run prek run --all-files`.

У CI це workflow `checks.yml`: він спрацьовує на кожен push у `develop`, `main`, `release/*` чи `hotfix/*` і на кожен PR — тобто й тоді, коли робота лягає в `develop` напряму, без PR. Реліз-гілки в цьому переліку тому, що `git flow release finish` зливає локально, без PR: підняту версію, переписаний змінник і readme вперше побачив би вже push у `main`, після злиття. А це запізно — `main` рухається лише релізом чи хотфіксом, тож червоний `main` звичайним комітом не лагодять. На тих самих двох гілках прокидається другий workflow, `release_checks.yml` — те, що має сенс ганяти раз на реліз, а не раз на коміт (нижче). `build_addon.yml` лишився суто складальним: PR, теґ `v*` або ручний запуск.

Тести не імпортують сам додаток: його модулі потребують живого NVDA. Під `unittest` лягає `core` — див. «Межа ядра й оболонки» вище.

Два тести сторожують переважно не код, а похідні від спеки файли. Перший — `tests/unit/test_schema.py` — тримає [`checklist-v1.schema.json`](checklist-v1.schema.json) при §2 спеки: валідує схемою кожен `json`-блок цілого файла зі спеки та з [`checklist-format.md`](checklist-format.md), ганяє фікстури `tests/fixtures/` (валідні мусять пройти, невалідні — впасти) і окремо перевіряє унікальність `id`, якої JSON Schema виразити не може. Схема є похідним файлом, і без цього тесту її узгодженість зі спекою трималася б на памʼяті.

Один блок у ньому дивиться у зворотний бік — на код: правила запису (§2) теж породжують файли, і файл, який записав сам додаток, мусить лишатися файлом задокументованого формату. Інакше схема була б правдою про кожен чекліст, окрім тих, що їх лишає по собі додаток. Звідси два обмеження на документацію: контрприклади в спеці й авторському документі подаються неповними прикладами або прозою, а не цілими файлами, а невалідні фікстури ламають рівно одну клаузу контракту валідації кожна — інакше зникнення клаузи зі спеки нікого не потривожить.

Потрібен `jsonschema` — він у групі залежностей `test` (`pyproject.toml`), тобто в аддон не потрапляє ніколи. Чому додаток не валідує схемою в рантаймі — §7.3 спеки.

Другий — `tests/unit/test_catalogue.py` — тримає український каталог при коді й при спеці. Каталог є похідним так само, як схема, і розходиться він у два боки, обидва мовчазні: неперекладений рядок звучить англійською, а переклад рядка, вилученого з коду, лишається у файлі. Тест читає `.po` власним розбором, дістає з кожного файла `i18nSources` рядки, віддані `_()` та `ngettext()`, і звіряє обидва напрямки; заразом ловить `fuzzy`, з яким рядок теж звучить англійською, хоч каталог і виглядає повним.

Він же перевіряє те, що §3.5 і §6 вимагають від самих команд: кожен скрипт несе `description`, загорнутий у `_()`, окрім одного — того, що ставить статус цифрою й навмисно лишається поза діалогом «Жести вводу». І він же читає словник статусів прямо зі спеки, бере з `wording.py` те, які `msgid` кожен статус озвучує, і перевіряє, що каталог каже саме ті слова. Три файли, по одному слову в кожному, і жодного переписаного в тест.

Позиції аргументів, із яких `xgettext` бере рядки, тест мусить читати так само, як їх читає збірка: `site_scons/site_tools/gettexttool` додає `--keyword=pgettext:1c,2`, де **перший** аргумент є контекстом, а не повідомленням.

**Локальний Pyright бачить `core/`, але не оболонку** — її перевіряє CI, який спершу викладає поруч вихідники NVDA (`pyrightconfig.ci.json`). Вона ловить саме той клас помилок, який інакше знаходиться лише на слух: неіснуючий метод NVDA виглядає в редакторі як справжній, а падає вже в скрінрідері. Перевірено на `scriptHandler.getLastScriptExecutionTime()` — функції, якої немає (§6 спеки): CI дає `"getLastScriptExecutionTime" is not a known attribute of module "scriptHandler"`.

**Проти якої саме NVDA.** Вихідники беруться не з `master`, а з релізу, названого `addon_lastTestedNVDAVersion` у `buildVars.py` (§6 спеки). `master` — це NVDA після наступної, і перевірка проти неї бреше в обидва боки: метод, доданий туди вже після релізу, пройде CI й упаде в користувача, а метод, звідти прибраний, завалить CI, хоча в тій NVDA, під якою аддон працює, він на місці. Обидва випадки інакше знаходяться вже на слух — тобто рівно там, куди ця перевірка й не пускає.

Номер при цьому не записано в YAML: його виводить із того самого поля `tools/nvda_ref.py`, і той самий виклик друкує ref.

```
uv run python -m tools.nvda_ref
```

**І проти якої ще.** `addon_lastTestedNVDAVersion` — лише верхній кінець того, що обіцяє маніфест. Нижній записано поруч, у `addon_minimumNVDAVersion` (§6 спеки), і NVDA цієї версії аддон встановить і запустить. API, що з'явився між ними, розв'язується проти верхніх вихідників, проходить кожен коміт і зникає в користувача, якого маніфест впустив. Це та сама помилка, що й перевірка проти `master`, лише пересунута на інший кінець діапазону, — і більше її не ловить ніщо: аддон розробляють на найсвіжішій NVDA, тож під найстарішою його не запускає ані CI, ані власний скрінрідер розробника.

Нижній кінець перевіряє окремий workflow — `release_checks.yml`. Це той самий pyright і той самий `pyrightconfig.ci.json`, лише вихідники NVDA називає друге поле:

```
uv run python -m tools.nvda_ref minimum
```

Перевірено на `braille.BrailleHandler.autoScroll` — методі, який у 2026.2 є, а у 2026.1 його ще немає. Та сама проба проти стелі дає `0 errors`, проти підлоги — `Cannot access attribute "autoScroll" for class "BrailleHandler"`. Тобто це рівно той код, який сьогодні проходив би кожен коміт і не запускався б у користувача, чия NVDA старша за вашу. Межа перевірки теж названа на пробі: через модуль `config` її не побудувати — у `config/__init__.py` є модульний `__getattr__`, тож ім'я, якого там немає, pyright вважає наявним на обох кінцях. Атрибут, узятий із самого `config`, підлога не стереже; те, що лежить у його підмодулях і класах, — стереже.

**Раз на реліз, а не раз на коміт.** Другий неглибокий клон NVDA — це ще близько 270 МБ і ще один прогін pyright. Платити це на кожному push і кожному PR немає за що: помилка може дійти до людини лише через реліз, а гілка `release/*` — водночас останній момент, коли виправити її ще дешево, і перший, коли вона щось важить. Звідси тригер: push у `release/*` чи `hotfix/*` і ручний запуск, яким перевірку кличуть одразу після того, як торкнулися API NVDA, не чекаючи релізу. Платить за це сама реліз-гілка — стільки прогонів, скільки разів у неї запушать, — і разом із ними отримує повний `checks.yml`, якого на ній раніше не було зовсім.

Ціна цього рішення одна, і її варто знати: **гілку треба запушити й дочекатися зеленого**. Реліз чи хотфікс, зроблений цілком локально, цієї перевірки не побачить ніколи, а зливає `git flow release finish` локально — тобто захисту гілок тут нема кому підставити плече. Тому push стоїть окремим кроком у списку §7, і зеленого чекають там-таки.

Гілки на реліз NV Access не тримає — уціліла одна, `release-2013.1`, — тож ref є **теґом**. Перший реліз циклу підписано двома числами, дальші — трьома: `2025.3.0` лежить під `release-2025.3`, а `2025.3.1` — під `release-2025.3.1`. Правило коротке, але не вгадується, тому його тримає `tests/unit/test_nvda_ref.py`, який заразом перевіряє, що версія в `buildVars.py` є такою, яку це правило вміє прочитати. Теґ, якого не існує, ловить сам `git clone --branch` і каже про це прямо.

Вікна аддона живуть на `wx`, а `wx` у вихідниках NVDA не лежить — це site-package. Тому в групі залежностей `lint` є `wxPython`, закріплений на версії, яку постачає NVDA з `addon_lastTestedNVDAVersion` (для 2026.2 — 4.2.4), і піднімається разом із нею. Лише для Windows: коліс для Linux PyPI не має, а sdist збирає wxWidgets із вихідників — звідси й `windows-latest` у `checks.yml` (§1).

Дає це імена, а не типи. Власні `.pyi` wxPython згенеровано sip: без `py.typed` і без жодної анотації повернення на 5749 функцій `core.pyi`. Під strict кожен `GetValue()` чи `ShowModal()` лишається «partially unknown»: пробний діалог на сорок рядків давав 24 помилки, і 19 із них були саме про це. Тому `pyrightconfig.ci.json` вимикає п'ять правил `reportUnknown*` і `reportMissingTypeStubs` — так само, як робить власна конфігурація NVDA, де ці правила підписано «20000+ errors». Вони міряють, скільки Pyright зміг вивести, а не чи існує те, що викликано. Увімкненими лишаються правила, заради яких перевірка існує: нерозв'язаний імпорт, неіснуючий метод (`ShowModel` замість `ShowModal` — помилка), аргумент не того оголошеного типу, `Optional` без перевірки (`gui.mainFrame` має тип `MainFrame | None`). Чого вона не зловить — одрук у ключовому аргументі конструктора: sip оголошує конструктори як `*args, **kw`.

Для ядра нічого не слабшає: правила `reportUnknown*` для `core/` тримає локальна перевірка (див. «Межа ядра й оболонки»), і CI проганяє її кроком `prek`.

Розглянуто й відхилено:

* сторонній `types-wxpython` — останній реліз 2024 року, стаби згенеровано з документації 4.2.0, і вони брешуть: `GetApp()` там ніколи не `None`, а `FileDialog.__enter__` повертає `None` і ламає `with`;
* власна заглушка через `stubPath` — точна рівно там, де написана, але кожен клас `gui`, якого торкається аддон, тягне в неї свою wx-поверхню (п'ять витоків уже на одній пробі панелі налаштувань), а брехню в ній CI побачити не може;
* глушіння лише `reportMissingImports` — знімає одну помилку з п'яти, решта є наслідком нерозв'язаного модуля.

`wx` аддон імпортує у трьох місцях — `commandmode` бере з нього `CallLater` для таймера режиму команд, `modal` показує й знищує вікна, `itemdialog` будує діалог пункту (§3.3.1 спеки), — тож зникнення самого пакета CI помітив би: нерозв'язаний `import wx` у строгому режимі є помилкою. **Поверхню контролів** — `TextCtrl`, `ComboBox`, `Button`, стилі, стокові ідентифікатори, `EndModal` — тримає тепер сам діалог пункту: він проходить цю перевірку разом з рештою оболонки, і одруківка в імені методу валить її так само, як валила б проба.

Доти поверхню тримала проба `tests/typecheck/probe_wx.py` — кілька рядків, які ніхто не імпортував і не запускав, — і з появою першого власного вікна вона пішла разом із текою `tests/typecheck` у `include` CI-конфігурації. Те, що в ній лишалося б непокритим (`ShowModal`, `GetApp()`), аддон не викликає ніде й викликати не буде: модальність йому піднімає `displayDialogAsModal` самої NVDA (§6 спеки). Наступне власне вікно приносить свою поверхню так само — своїм кодом, а не пробою поруч.

Те саме локально (неглибокий клон важить близько 270 МБ, а не гігабайт; wxPython ставить звичайний `uv sync` на Windows):

```
git clone --depth 1 --branch $(uv run python -m tools.nvda_ref) https://github.com/nvaccess/nvda.git ../nvda
uv run pyright --project pyrightconfig.ci.json
```

Підстановка тут працює і в bash, і в PowerShell, тож рядок один на обидві оболонки.

**Наявний клон ця команда не оновлює**, і тиха половина цього гірша за гучну. Гучна: `git clone` відмовиться писати в теку, яка вже є, і на тому спиниться. Тиха: клон, залишений у `../nvda` від попереднього разу, нікуди не подінеться — і якщо він із `master`, локальна перевірка піде рівно проти того, від чого CI щойно відмовився, не подавши жодної ознаки. Перевести наявний клон на потрібний теґ дешевше, ніж викачувати заново:

```
git -C ../nvda fetch --depth 1 origin tag $(uv run python -m tools.nvda_ref)
git -C ../nvda checkout $(uv run python -m tools.nvda_ref)
```

Усе це бере верхній кінець діапазону. Щоб прогнати в себе нижній — той, що його ганяє `release_checks.yml`, — до виклику додається слово `minimum`:

```
git -C ../nvda fetch --depth 1 origin tag $(uv run python -m tools.nvda_ref minimum)
git -C ../nvda checkout $(uv run python -m tools.nvda_ref minimum)
uv run pyright --project pyrightconfig.ci.json
```

Після цього клон лишається на старій NVDA, і тиха пастка, описана щойно, чекає вже на наступний прогін проти верхнього кінця: він піде проти підлоги й нічого про це не скаже. Повертає клон на місце той самий виклик без `minimum`.

**Що йде за яким полем.** Полів тепер двоє, і тягнуть вони за собою різне.

Піднявши `addon_lastTestedNVDAVersion`, піднімають разом із ним:

* **ref вихідників NVDA** — виводиться з поля, руками робити нічого;
* **`pythonVersion` у `pyrightconfig.ci.json`** — версія Python, яку виконує та NVDA (для 2026.2 — 3.13), тож синтаксис, новіший за неї, не пройде;
* **`wxPython` у групі `lint`** (`pyproject.toml`) — версія, яку та NVDA постачає (для 2026.2 — 4.2.4, вище);
* **датовані твердження спеки.** Кілька місць у `requirements.md` описують поведінку NVDA, якої перевірка типів не бачить, і кажуть, по джерелах якої версії її читали: §3 (вільні комбінації під `NVDA+Alt`), §3.1 (стрілки Лупи), §3.3.1 (де зв'язано `control+enter`), §6 (лічильник модальності й `wx.FileDialog`; умова `getDialogText`). Кожне перечитується проти вихідників нової стелі й передатовується — це ті самі `git grep` по теґу, що й вище. Окремо стоїть вимірювання на wxWidgets у §3.3.1 і в коментарях `itemdialog.py` та `fragmentsdialog.py`: воно зроблене на живій збірці, тож передатовується лише після того, як на новій NVDA пройдено на слух обхід Tab у діалозі пункту та `Enter` у списку фрагментів (крок 10 у §7). Твердження, яке після звірки не тримається, є правкою спеки, а не цифри.

Змінивши `addon_minimumNVDAVersion`, не піднімають нічого: ref другого прогону виводиться з поля так само, а обидва числа вище описують поки що обидва кінці одразу. NVDA 2026.1 виконує той самий Python 3.13 і постачає той самий wxPython 4.2.4, що й 2026.2, — тому `release_checks.yml` бере незмінений `pyrightconfig.ci.json`, а не власну копію.

**Це збіг, а не правило, і перевіряти його — робота верхнього поля.** `pythonVersion` у файлі рівно один, тож щойно підняте `addon_lastTestedNVDAVersion` принесе Python, новіший за той, що виконує підлога, одним конфігом два прогони не обійдуться — нижньому знадобиться свій. Із `wxPython` межа інша, але наслідок той самий: група `lint` тримає одну версію на обидва прогони, і розійшовшись, один із кінців перевірятиме вікна проти чужих стабів. Обидві версії оголошує сама NVDA, у теґу, який і так викладено поруч, — але **де саме, між релізами переїжджає**: у 2025.1 це `requirements.txt` і `appveyor.yml`, у 2025.3 їх обох уже немає, а числа лежать у `pyproject.toml` і `.python-versions` — і у 2026.1 та 2026.2 там само. Тож звірку роблять пошуком по вихідниках, а не за адресою.

Числа записані навмисно. Вивести їх із викладених вихідників у принципі можна, але кроком, який переписував би комітований конфіг просто в CI, — після чого локальний прогін перевіряв би не те, що перевірив CI, і розбіжність між ними неможливо було б відтворити в себе.

## 5. Від'єднання

```
powershell -ExecutionPolicy Bypass -File tools\dev-link.ps1 -Remove
```

Скрипт знімає саме посилання й відмовляється працювати, якщо на місці посилання виявилася справжня тека.

**Не видаляй dev-посилання через Add-on Store.** NVDA видаляє аддон так: перейменовує теку, далі `shutil.rmtree` (`addonHandler.Addon.completeRemove`). Python ≥ 3.11 трактує junction як посилання й усередину не заходить, тож файли репозиторію вціліють, але `rmtree` завершиться помилкою, яку `ignore_errors=True` проковтне: посилання лишиться на диску, а стан аддона в NVDA — зіпсованим.

З тієї ж причини не знімай посилання через `Remove-Item` у Windows PowerShell 5.1: там воно заходить у ціль і видаляє вміст. Скрипт видаляє лише точку повторного розбору.

## 6. Коли аддон ламає NVDA

Помилка в глобальному плагіні може лишити машину без озвучення, тож запобіжники варто знати **до** першого запуску:

* `Ctrl+Alt+N` — перезапуск NVDA.
* Меню NVDA → *Вийти* → **«Перезапустити з вимкненими аддонами»**.
* `nvda.exe --disable-addons` — те саме з командного рядка.
* `NVDA+F1` — переглядач логу; повний файл — `%TEMP%\nvda.log`. Рівень *Debug* у *Параметри NVDA → Загальні* показує трасування наших виключень.

## 7. Реліз

Наскрізний прохід: від відгалуження реліз-гілки до появи версії в Add-on Store. Хотфікс описано нижче — різницею до цього проходу, а не другим списком.

Форму всьому задає одна обставина: **публікацію запускає push теґа**. Усе до нього зворотне й коштує одного коміта; усе після має ціну, і межу названо в «Коли щось пішло не так».

Що означає сам номер версії — §7 спеки; сюди він приходить уже обраним.

### Підготовка

1. **Оновити `develop`.**

```
git checkout develop
git pull
```

`git flow release start` фетчить, але гілку створює з **локальної** `develop`, а не з `origin/develop`. Без цього кроку в реліз поїде те, що лежить на диску.

2. **Відгалузити реліз.**

```
git flow release start 0.1.0
```

Ім'я голе, без префікса: з `release/0.1.0` вийшла б гілка `release/release/0.1.0`.

3. **Підняти `addon_version` у `buildVars.py`** до номера релізу — саме в цій гілці, щоб теґ `vX.Y.Z` ліг на той самий коміт.

4. **Переписати `changelog.md`** під цю версію (§2) і привести до неї `addon_changelog` у `buildVars.py`.

5. **Долити український каталог.** `addon_changelog` загорнутий у `_()`, тобто перекладний, і правка з кроку 4 лишає каталог позаду. Забути це не вийде тихо — `tests/unit/test_catalogue.py` почервоніє, — але почервоніє воно вже на реліз-гілці.

```
scons pot
msgmerge --update addon/locale/uk/LC_MESSAGES/nvda.po axygenChecklist.pot
```

Далі перекласти новий рядок. Якщо фільтр `cleanpo` не налаштовано (§1), номери рядків прибрати руками:

```
msgcat --no-location -o addon/locale/uk/LC_MESSAGES/nvda.po addon/locale/uk/LC_MESSAGES/nvda.po
```

6. **Оновити блок «чого ще немає в цій версії» в обох readme** — `readme.md` і `addon/doc/uk/readme.md`. Він перелічує поіменно те, чого в цій версії ще немає (§7.2 спеки), і застаріває з кожним релізом. Загальна фраза «щось іще реалізується» його не замінює: саме перелік не дає користувачеві шукати команду, якої немає, і саме він щоразу застаріває непомітно.

7. **Звірити межі сумісності з магазином.** `addon_minimumNVDAVersion` і `addon_lastTestedNVDAVersion` мусять бути серед версій у [`nvdaAPIVersions.json`](https://github.com/nvaccess/addon-datastore/blob/master/transform/nvdaAPIVersions.json), і для каналу `stable` — не мати там позначки `"experimental": true`.

Аддон видно з тієї NVDA, у якої `backCompatTo` не перевищує наш `lastTestedNVDAVersion`, тобто стеля мусить бути не нижчою за `backCompatTo` **кожної** неекспериментальної NVDA в таблиці. NVDA з новішим `backCompatTo` не покаже його в списку взагалі — `transform.py` магазину такий аддон не відхиляє, а мовчки не вносить до списку, — а встановлений вручну вимкне як несумісний: те саме число вона тримає у власній константі `addonAPIVersion.BACK_COMPAT_TO`. Заразом глянь на експериментальні рядки: якщо в котрогось `backCompatTo` уже вищий за нашу стелю — як у 2027.1 станом на вересень 2026, — з його виходом знадобиться реліз із новою стелею. Числа ростуть без нас, тож звіряти їх треба щоразу, а не один раз назавжди: у 2026 році стеля 2025.3 півроку робила аддон невидимим для кожної чинної NVDA і заблокованим на машині розробника (#31).

### Перевірка

8. **Запушити гілку й дочекатися зеленого.**

```
git flow release publish
```

На `release/*` — і так само на `hotfix/*` — прокидаються обидва workflow: `checks.yml` із лінтом, типами й тестами і `release_checks.yml` із перевіркою проти найстарішої підтримуваної NVDA (§4). Другої реліз, зроблений цілком локально, не побачить ніколи, а стереже вона саме те, що ламається лише в користувача, чия NVDA старша за вашу. Зливає `git flow release finish` локально, тож захисту гілок тут нема кому підставити плече: крім цього кроку, червоного не спинить ніщо.

`publish` одноразовий: удруге він відмовить, бо гілка на `origin` уже є. Правки, зроблені після нього, доштовхуються звичайним `git push`.

Складання пакета в це зелене **не входить** — `build_addon.yml` на реліз-гілках не прокидається. Тому наступні два кроки робляться руками.

9. **Зняти dev-посилання** (§5). Воно перевіряє код, але не перевіряє ані пакет, ані документацію, яка в ньому їде.

```
powershell -ExecutionPolicy Bypass -File tools\dev-link.ps1 -Remove
```

10. **Зібрати й перевірити пакет.**

```
scons
```

Встановити зібраний файл (*Інструменти → Add-on Store → Встановити зі стороннього джерела*, або просто відкрити його) і перезапустити NVDA. Перевірити встановлення, оновлення поверх попередньої версії та штатне видалення.

### Завершення й публікація

11. **Завершити реліз.**

```
git flow release finish 0.1.0
```

Що саме відбувається, по порядку: `main` зливає реліз-гілку — типово fast-forward, тобто `main` просто переїжджає на її вершину; теґ `v0.1.0` стає на цей самий коміт; далі `develop` зливає `main`, уже жорстким `--no-ff`; наприкінці видаляються локальна й **віддалена** реліз-гілки. Лишаєтеся ви на `develop`, не на `main`.

Віддалена гілка зникає навмисно — CI на ній уже відпрацював. Якщо вона ще потрібна, `--keepremote` її лишає.

Команда **нічого не пушить**. Ключ `gitflow.release.finish.push` існує, але ми його не заводимо: push теґа незворотний, і ховати незворотну дію за замовчуванням не варто. До того ж значення читається з git config, а не з `.gitflow` напряму, тож ключ, дописаний у файл без `git flow config sync`, мовчки не діятиме — стан «написано одне, працює інше» гірший за явну команду.

12. **Запушити.** Саме push теґа запускає публікацію.

```
git push origin main develop --follow-tags
```

13. **Дочекатися `build_addon.yml`.** На теґ `v*` він збирає `.nvda-addon` і `.pot` на `ubuntu-latest`, дописує `SHA256` у `changelog.md` **у раннері** (у репозиторій це не комітиться) і публікує GitHub-реліз із обома файлами. Тіло релізу — `changelog.md` цілком, тому файл і містить лише ту версію, що виходить (§2).

14. **Перевірити опублікований пакет.** `.nvda-addon` із релізу зібрано в CI на Linux — це **не** той файл, що вийшов на кроці 10. Завантажити його, встановити й переконатися, що аддон запускається: далі саме за цим URL ходитиме магазин.

15. **Повернути `develop` у сентинел-стан.** Злиття з кроку 11 принесло в `develop` номер релізу, його змінник і його `addon_changelog`. Лишити їх означало б, що пакет із будь-якого PR у `develop` назветься так само, як справжній реліз, і матиме інший вміст.

```
git checkout develop
```

Повернути всі три: `addon_version` → `"0.0.0"`, `changelog.md` і `addon_changelog` → рядок про ще не випущену версію. Сентинел цінний саме тим, що його не сплутати з релізом; напівсентинел плутається гірше за жоден.

16. **Подати в Add-on Store** — нижче.

### Подання в Add-on Store

Подання — це **issue-форма** в `nvaccess/addon-datastore`, а не pull request. Бот розбирає форму, качає `.nvda-addon` за вказаним URL, сам рахує SHA256, генерує файл версії з нашого ж маніфеста, відкриває PR і зливає його. Рукописний PR там не проходить жодної перевірки — його просто не чекають.

Форма питає те, чого в маніфесті немає: URL завантаження (асет GitHub-релізу з кроку 13), URL джерел, видавця, канал і ліцензію. Решту — назву, опис, версію, обидві межі NVDA, переклади — бот бере з `manifest.ini` усередині пакета. `SHA256`, який workflow дописав у тіло релізу, у поданні не бере участі: бот рахує свій. Той рядок лишається довідкою для людини.

**Першу подачу аддона гейтить людина** — до двох тижнів, поки нас не внесуть у список довірених. Оновлення вже схваленого аддона проходять без цього.

Актуальні поля, посилання на форму й самі правила — у [`submissionGuide.md`](https://github.com/nvaccess/addon-datastore/blob/master/docs/submitters/submissionGuide.md). Тут записано лише те, що є рішенням **цього** проєкту.

Канал (`stable` / `beta` / `dev`) **не є властивістю пакета**. NVDA не читає `updateChannel` із `manifest.ini` взагалі: у схемі маніфеста такого ключа немає, а в коді Add-on Store `updateChannel` означає користувацьке налаштування на кожен аддон. Канал обирається у формі подання; поле `addon_updateChannel` у `buildVars.py` лишається `None`, як у шаблоні, бо воно ні на що не впливає.

Подаємо **на `stable`, включно з версіями `0.x`**. Типове налаштування оновлень у NVDA — `SAME`: автоматичні сповіщення шукають нову версію у тому самому каналі, з якого аддон встановлено. Реліз 0.x на `beta` означав би, що про вихід 1.0.0 на `stable` наявні користувачі не дізнаються ніколи — побачать його лише ті, хто сам відкриє Add-on Store і подивиться. Тобто канал замовчав би нас рівно в той момент, заради якого 1.0.0 і робиться. Сигнал «може зламатися» вже несуть номер `0.x`, блок «чого ще немає» в readme і змінник; четвертий зайвий. Версії нижче 1.0.0 на stable — звичайна річ, їх там кілька сотень.

Два обмеження магазину, які краще знати заздалегідь:

* **Номер версії — `X.Y` або `X.Y.Z` з цілих чисел.** Суфікси на кшталт `-rc1` валідатор datastore відхиляє, тож теґів із дефісом у цього проєкту не буває — звідси й відсутність умови `prerelease` у `build_addon.yml`. Заразом: `1.0` і `1.0.0` при перевірці оновлень **рівні**, а номер версії унікальний на аддон через **усі** канали, тобто той самий номер не можна подати і на beta, і на stable.
* **Stable-подання відхиляють**, якщо `minimumNVDAVersion` або `lastTestedNVDAVersion` вказує на NVDA, ще позначену `experimental` (alpha чи beta). Це та сама звірка, що на кроці 7, лише з боку магазину.

### Коли щось пішло не так

Межа проходить по **злиттю бот-PR у магазині**.

До нього все зворотне: теґ і реліз наші, і той самий номер можна перевипустити.

```
gh release delete v0.1.0 --yes
git push origin :refs/tags/v0.1.0
git tag -d v0.1.0
```

`main` при цьому лишається там, де стоїть: відкочувати її не треба, бо правка приходить хотфіксом і теґується тим самим номером. Якщо подання вже відкрите, але PR іще не злито — закрити issue подання.

Після злиття номер спалено: магазин відмовляє будь-якій зміні наявного файла версії словами «already present in the Add-on Store with the same version number». Лікується лише наступним PATCH.

І окремо, назавжди: **опублікований реліз-асет не видаляти**. URL має лишатися чинним, і це не побажання — магазин щомісяця перекачує кожен аддон і виносить зі списку ті, чий файл не качається або змінив хеш.

### Хотфікс

Той самий прохід, із `main` замість `develop` як початком.

```
git checkout main
git pull
git flow hotfix start 0.1.1
```

Відмінностей три:

* **Крок 6 не робиться.** Хотфікс за §7.1 спеки є PATCH, тобто поведінки не змінює, і переліку «чого ще немає» нема від чого застарівати.
* **Крок 4 важить більше, ніж здається.** Гілка бачить `changelog.md` і `addon_changelog` **випущеної** версії, а не сентинел; не переписати їх означає видати GitHub-реліз, тіло якого описує минулий реліз.
* **Крок 8** — `git flow hotfix publish`. Обидва workflow на `hotfix/**` прокидаються так само.

Решта — кроки 3–5, 7, 9–10 і 12–15 — без змін. Крок 11 відрізняється лише командою: `git flow hotfix finish 0.1.1` поводиться як реліз-варіант — зливає в `main`, теґує, зливає `main` у `develop` і лишає вас на `develop`, нічого не пушачи. Тобто крок 15 потрібен і тут.

## 8. Відхилені варіанти

**Developer Scratchpad** — `%APPDATA%\nvda\scratchpad\globalPlugins\`, вмикається в *Параметри NVDA → Додатково → «Увімкнути завантаження власного коду з теки Developer Scratchpad»*. Офіційний спосіб швидко перевірити код, сумісний і з посиланням, і з `NVDA+Ctrl+F3`. Відхилено: код у scratchpad не належить жодному аддону, тому `addonHandler.initTranslation()` там завершується помилкою — Developer Guide формулює це прямо. Спека (§6, «Локалізація») вимагає цей виклик у кожному модулі з `_()`, тож у scratchpad додаток або не запуститься, або запуститься лише з тимчасово вирізаною локалізацією — тобто перевірятиметься не той код, що піде в реліз. Додатково scratchpad не бачить `manifest.ini`, теки `addon/locale` і перевірки сумісності.

**Збирати й встановлювати `.nvda-addon` на кожну правку.** Відхилено як щоденний цикл: кожна ітерація коштує перезапуску NVDA. Лишається обов'язковим кроком перед релізом (§7).
